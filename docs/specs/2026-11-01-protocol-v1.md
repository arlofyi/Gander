# Spec: Gander protocol v1 (host <-> client)

- Status: Draft for implementation (Phase 1; Stream parts land in Phase 2)
- Date: 2026-11-01
- Related: `2026-11-01-pairing-and-trust.md` (auth), `2026-11-01-path-resolution.md` (paths),
  `2026-11-01-stream-launch-policy.md` (stream), ADR-0005 (transport)

## Goals

- One port, one TLS listener, plain HTTP/1.1 + WebSocket. Any language can implement a client.
- Every request is authenticated by a per-device bearer token except the two pairing endpoints and
  the minimal `GET /v1/host`.
- The client can always explain state honestly: capabilities are advertised, every refusal has a
  machine-readable code, and nothing is "discovered after a spinner".
- Versioned from day one. Breaking changes mean `/v2/`; additive changes are advertised in
  `capabilities`.

## Transport

- TLS 1.3 only (rustls). Host certificate: self-signed ECDSA P-256, 10-year validity, CN = host id.
  Clients pin the SPKI SHA-256 learned at pairing and ignore the system trust store for this host.
- Default port **42637** ("GANDR" on a keypad), configurable. The host listens on loopback plus
  every private-network address it has decided to serve (see ADR-0002 and the pairing spec).
- HTTP/1.1 with keep-alive. No HTTP/2 requirement. Max request body 64 KiB except where noted.
- WebSocket at `/v1/events` for push events and stream signalling. Ping every 20 s; drop after
  two missed pongs.

## Authentication and request rules

- `Authorization: Bearer <token>` on every request except `GET /v1/host`, `POST /v1/pair`,
  `GET /v1/pair/{id}`. Tokens are 32 random bytes, base64url, see the pairing spec.
- Requests carrying an `Origin`, `Sec-Fetch-Mode` or `Cookie` header are refused with 403
  `browser_request`. Gander has no browser client; this closes DNS rebinding and CSRF by
  construction. No CORS headers are ever sent.
- `Host` header must equal one of the addresses the host is serving (or `localhost` on loopback);
  otherwise 400 `bad_host`.
- GET and HEAD never change state. All mutations are POST or DELETE.
- Per-device concurrency: 8 in-flight requests; excess receive 429 `too_many_requests` with
  `Retry-After`. Thumbnail and preview generation have their own queue (below).
- Every response carries `X-Gander-Protocol: 1` and `X-Gander-Request: <ulid>` (logged locally,
  useful in bug reports).

## Error format

```json
{ "error": { "code": "share_not_found", "message": "human readable, English, no paths", "retry_after_ms": 0 } }
```

| HTTP | code | when |
| --- | --- | --- |
| 400 | `bad_request`, `bad_host`, `bad_path` | malformed input; `bad_path` covers every resolver rejection except not_found |
| 401 | `token_missing`, `token_invalid`, `token_revoked` | the client must forget the host on `token_revoked` after showing why |
| 403 | `forbidden`, `browser_request`, `network_identity_mismatch`, `permission_denied` | `permission_denied` names the missing permission in `message` |
| 404 | `share_not_found`, `not_found`, `pairing_closed` | not_found is also used for hidden_patterns and denied reparse points |
| 409 | `stream_busy`, `pairing_in_progress` | |
| 410 | `pairing_expired` | |
| 412 | `host_locked`, `host_unattended`, `app_unavailable` | stream preconditions |
| 413 | `too_large` | body or requested preview dimension over limit; a folder over the zip limits |
| 415 | `unsupported_type` | no preview or thumbnail for this type |
| 422 | `stream_refused` | file type or handler refused by policy; `message` says why in user terms |
| 429 | `too_many_requests`, `pairing_rate_limited` | |
| 500 | `internal` | never includes details |
| 503 | `generating` | thumbnail/preview not ready yet; `retry_after_ms` set |

## Endpoints

All paths are prefixed `/v1`. Share-relative `path` query values are percent-encoded UTF-8 with
`/` separators; see the path-resolution spec for what is accepted.

### Host and identity

`GET /host` (no auth). Deliberately minimal so an unpaired tailnet peer learns almost nothing.
```json
{ "protocol": [1], "pairing_open": false, "host_id": "<spki-sha256-b64url>" }
```

`GET /me`
```json
{
  "device": { "id": "dev_01J...", "name": "Pixel 9", "created_at": "...", "last_seen_at": "..." },
  "host": { "id": "...", "name": "studio-pc", "os": "windows", "os_version": "10.0.26200", "app_version": "0.1.0",
            "addresses": ["100.101.102.103", "fd7a:115c:a1e0::1"], "magic_dns": "studio-pc.tail1234.ts.net" },
  "network": { "adapter": "tailscale", "identity": { "login": "alice@example.com", "node": "pixel-9" }, "relayed": null },
  "capabilities": {
    "list": true, "search": true, "recent": true, "events": true,
    "thumb_sizes": [128, 256, 512], "preview_max_width": 2048,
    "preview_kinds": { "image": true, "pdf": true, "text": true, "office": "thumbnail|render|none", "video_poster": true, "raw": true },
    "fetch": { "range": true, "hash": ["blake3", "sha256"], "zip": { "max_bytes": 4294967296, "max_entries": 20000 } },
    "stream": { "enabled": true, "codecs": ["h264", "hevc"], "max_sessions": 1, "audio": false, "input": true, "fit_to_phone": true },
    "write": false
  },
  "limits": { "list_max": 1000, "search_max": 500, "concurrency": 8 }
}
```

`POST /token/rotate` -> `{ "token": "<new>" }`. The old token stops working immediately.

### Pairing

Defined in `2026-11-01-pairing-and-trust.md`. Summary:

- `POST /pair` body `{ "secret": "<from QR, optional>", "device": { "name", "platform", "model", "app_version" }, "nonce": "<16 bytes b64url>" }`
  -> 200 `{ "pairing_id", "sas": "482 913", "host_nonce", "expires_at" }`, or 404 `pairing_closed`, 429.
- `GET /pair/{pairing_id}` -> 202 `{ "state": "pending" }` | 200 `{ "token", "device_id", "host": {...} }` | 403 `{ "state": "denied" }` | 410.
  Poll every 1-2 s; the host answers within 10 s of the owner's click.

### Shares

`GET /shares`
```json
{ "shares": [ { "id": "shr_01J...", "name": "Projects", "path_display": "D:\\Projects", "permissions": ["list", "preview", "fetch", "stream"],
                "show_hidden": false, "stream_default": "ask", "search": "indexed" } ] }
```
`path_display` is included only if the owner enabled "show folder path to devices" for the share.
`search` (optional, WP-66) is how `/search` works in this share: `true` (the bounded walk over names)
or `"indexed"` (the share's folder is in the Windows Search index, which is faster and also finds
text inside files). `capabilities.search` in `/me` is the host-level summary: `"indexed"` when at
least one share the device can list is indexed. A host that predates the field omits it; read it as
`capabilities.search` then.

### Browse

`GET /shares/{share}/list?path=&cursor=&limit=200&sort=name|mtime|size|kind&order=asc|desc&kinds=file,dir&ext=pdf,pptx`
```json
{
  "path": "Clients/Acme", "entries": [
    { "name": "Deck.pptx", "kind": "file", "size": 48213001, "mtime": "2026-10-30T09:12:44Z", "ctime": "...",
      "ext": "pptx", "mime": "application/vnd.openxmlformats-officedocument.presentationml.presentation",
      "flags": ["cloud_only"], "thumb": true, "preview": "office", "stream": "allowed|refused|ask" }
  ],
  "next_cursor": null, "truncated": false, "unlistable": 0, "etag": "W/\"...\""
}
```
- Directories sort first regardless of `sort` unless `kinds=file`.
- `thumb` is a prediction (type is thumbnailable), not a promise that generation will succeed.
- `preview` is the preview kind the host would produce: `image | pdf | text | office | video_poster | none`.
- `stream` is the policy outcome for this device and file: `allowed`, `refused` (with no reason here;
  the client calls `POST /stream` to get the reason) or `ask` (host owner will be prompted).
- Supports `If-None-Match` -> 304. The ETag is a hash of the entry list.

`GET /shares/{share}/stat?path=&meta=1`
Entry as above plus, with `meta=1`, type-specific metadata the host can get cheaply:
`image: { width, height, orientation, taken_at, camera }`, `video: { width, height, duration_ms, codec }`,
`pdf: { pages }`, `audio: { duration_ms, title, artist }`, `office: { pages: null | n }`.

`GET /shares/{share}/search?q=&path=&limit=100&cursor=&scope=name|content`
Case-insensitive substring match on names under `path`;
`{ "entries": [...with "path" field...], "partial": true|false, "next_cursor", "via": "index"|"walk" }`.
`via` (optional) says what answered:

- `walk`: breadth-first over the folders, bounded to 2 s of host time or `limit` results. Names
  only. This is the answer for a folder the index does not cover, when the Windows Search service
  is off, and after any error talking to it.
- `index` (WP-66): the Windows Search index, asked when the folder is inside its crawl scope
  (`ISearchCrawlScopeManager::IncludedInCrawlScope`, read only: Gander never changes the indexer's
  scopes or settings). Ordered by path (by relevance for `scope=content`).

`scope` (optional, default `name`; anything else is `bad_request`): `name` matches file and folder
names; `content` also matches the text inside files (every word typed has to occur, the last one may
be a prefix). Only the index can read file text: on a share searched by the walk, `scope=content` is
answered as a name search and `via: "walk"` tells the client so. A client shows "Search inside files"
only for a share whose `search` is `"indexed"`.

Index answers are held to exactly the rules of a listing. Every path the index returns is treated as
untrusted: the host builds the share-relative path from it and resolves it with the path resolver
(segment by segment, hidden patterns, no links or junctions, no alternate data streams or 8.3
aliases, final handle inside the share); an item the resolver or the listing filter would refuse
(hidden or system files unless the share shows them, `desktop.ini`, anything below a hidden
folder) is dropped, and size, times and flags come from the file, not from the index. Rows in a
name search are also checked against the stored name. Permissions are `list`, as for the walk.

`partial` is also `true` when the index is still crawling (its incremental queue is not empty), when
the page stopped at the 2 s budget (a `next_cursor` is then present), or when the result list
reached the host's depth limit (20,000 rows). The cursor is opaque. A cursor for an index search
(`i1.` prefix) is bound to the share, folder, text and scope of the search that made it (another
query: `bad_request`) and counts index rows, not results; a walk cursor (`s1.`) always continues the
walk. An index cursor whose index is no longer usable restarts the search as a walk; clients merge
results by `path`, so nothing is lost.

`GET /recent?limit=50&since=<iso>`
Files modified recently across all shares visible to this device, newest first, same entry shape
plus `share` and `path`. Host caches the walk for 60 s and bounds it (top 3 directory levels or
20,000 entries, whichever first), reporting `partial`.

### Thumbnails and previews

`GET /shares/{share}/thumb?path=&size=256`
- `image/webp` (fallback `image/jpeg`), longest side = size, EXIF orientation applied, no metadata.
- Strong ETag derived from (file id, size, mtime, generator version); `Cache-Control: private, max-age=31536000, immutable`.
- 503 `generating` with `retry_after_ms` while queued; 415 if the type is not thumbnailable; 404 as
  usual. Generation is a host-side queue with concurrency 2 and low process priority; the client
  should request thumbs for visible rows first and cancel on scroll.

`GET /shares/{share}/preview/info?path=`
```json
{ "kind": "pdf", "pages": 42, "width": 1240, "height": 1754, "text_bytes": null, "renderer": "windows_pdf", "estimated_ms": 400 }
```
`GET /shares/{share}/preview?path=&page=1&width=1080&format=webp|jpeg`
- `kind=image`: resized original (max width 2048). `kind=pdf|office`: rendered page. `kind=video_poster`: poster frame.
- 503 `generating` as for thumbnails; previews run on their own queue (concurrency 1 per device, 2 total).
- Office previews use the best available renderer on the host in this order: embedded thumbnail
  (page 1 only, low fidelity), Office COM export (Windows with Office installed, full fidelity),
  LibreOffice headless if installed, else `preview: "none"` and the client suggests Stream or Fetch.

`GET /shares/{share}/preview/tile?path=&page=1&level=&x=&y=`  (WP-67)
- One 512 x 512 `image/webp` tile of a page, for deep zoom past the width `preview` renders.
  `preview/info` carries the pyramid: `tile_size` (512), `tile_levels` and `tile_pages` (`width`,
  `height`, `levels` of the top level per page); absent when no page is large enough to need it.
  Level 0 is the whole page fitted in 512, each level doubles the one below, the top level is the
  natural resolution (an image's pixels, a PDF page at 300 dpi). Tiles are numbered from the top
  left; edge tiles are smaller. Shared test vectors: `protocol/test-vectors/tiles.json`.
- `level`, `x` and `y` are required. A level, column, row or page that does not exist is 400
  `bad_request`; a file without tiles (text, video, PowerPoint slides) is 415 `unsupported_type`;
  503 `generating` as for pages, with tiles queued behind pages on the same queue.
- Strong ETag from (file version, page, level, x, y), `Cache-Control: private, max-age=31536000,
  immutable`.

`GET /shares/{share}/preview/text?path=&offset=0&limit=65536`
- `text/plain; charset=utf-8` after encoding detection (BOM, UTF-8, UTF-16, else Windows-1252 best
  effort); `X-Gander-Text-Encoding` reports what was detected; `X-Gander-Text-Total` the file size.
  Hard cap 1 MiB per request. Binary files (NUL in first 8 KiB) -> 415.

### Fetch

`GET /shares/{share}/file?path=`  (HEAD supported)
- Streams bytes from the resolved handle. `Accept-Ranges: bytes`, `Content-Length`, strong `ETag`
  (file id + size + mtime), `Last-Modified`, `Content-Type` by extension,
  `Content-Disposition: attachment; filename*=UTF-8''...`.
- Honors `Range` (single range only; multipart ranges -> 416) and `If-Range`. Changed file during a
  resumed download -> 412 `file_changed` so the client restarts.
- `cloud_only` files: the host opens them normally (this hydrates the placeholder). The client
  warns before fetching a cloud-only file on a metered connection.
- No size limit; the client decides about cellular warnings using `size` from the listing.

`GET /zip?share=<id>&path=<folder>[&dry_run=1]`  (HEAD supported) -- folder download (WP-68)
- Needs the `fetch` permission. Sent only on an explicit request from the user: a client shows
  the size and entry count first (from `dry_run=1`, below) and never starts one by itself.
- Streams the folder (the share root when `path` is empty) as ONE ZIP archive, straight from disk
  through a bounded buffer: nothing is staged on the computer. Entries are STORED (not
  compressed; the files people fetch are already compressed). ZIP64 is used when an entry or the
  archive needs it. Everything is inside a top-level folder named after the folder (the share's
  name for the root). `Content-Type: application/zip`, `Content-Disposition: attachment` with the
  folder name and `.zip`.
- The walk uses the path resolver for every directory and every file, so it follows exactly what
  a listing shows: hidden and system files only if the share shows them, the always-omitted names
  (`desktop.ini`, ...), `hidden_patterns`. Links, junctions and mount points are NOT followed;
  they, and names that cannot be sent, are listed (path and reason, no contents) in
  `_gander-skipped.txt` at the end of the archive, as is anything that vanished or could not be
  read while the archive was being made. The note is only written when something is listed.
- Limits, set by the owner in `config.toml` `[zip]` and advertised as `capabilities.fetch.zip`
  (`max_bytes`, default 4 GiB; `max_entries`, default 20,000, files and folders below the folder
  asked for) plus a 30 s measuring budget. The host measures the folder with a bounded walk that
  stops at the first limit crossed and answers `413 too_large` BEFORE streaming anything.
- `dry_run=1`: nothing is streamed; the answer is JSON `{ "entries", "bytes", "skipped",
  "cloud_only" }` (the same totals the real download is limited by; `cloud_only` counts cloud
  placeholder files that zipping would make the computer download first, so the client can warn).
- The length is not known in advance (chunked transfer, no `Content-Length`); the measured totals
  are in `X-Gander-Zip-Entries` and `X-Gander-Zip-Bytes` for a progress display. **There is no
  `Range`, `If-Range` or resume**: those headers are ignored (always 200, the whole archive from
  the start), `Accept-Ranges: none`, and a broken download starts over. The host stops reading
  when the client disconnects.
- Each file is read when its turn comes, up to the size measured: a file that grew meanwhile is
  cut there (and noted), a file that is shorter is sent as it is, and a file that shrinks while it
  is being read ends the download with a broken connection (never a padded entry). The archive is
  not a snapshot of the folder.
- At most two zips stream at once on a host; another is `429 too_many_requests` with
  `Retry-After`. One `fetch` audit event (`kind: "zip"`) records the folder path, the entry count
  and the bytes sent when the download ends; file names are never logged.

`GET /shares/{share}/hash?path=&algo=blake3|sha256`
-> `{ "algo": "blake3", "hex": "...", "size": n, "etag": "..." }` or 503 `generating`. Cached on the
host by ETag per algorithm. Clients verify after a completed download when the user enabled
"verify downloads" (default on for files over 50 MiB); `sha256` exists for clients without a
BLAKE3 implementation.

### Events (WebSocket)

`GET /events` with the bearer token in the `Authorization` header (the Android client uses OkHttp
so headers work; browsers are not a target). Messages are JSON text frames `{ "type": ..., ... }`.

Server -> client:
- `hello { protocol, host_time }`
- `share.changed { share, path }` (debounced 500 ms, from ReadDirectoryChangesW on shares that
  have been listed by this device in the last 10 minutes)
- `shares.updated {}` (owner added/removed a share or changed permissions)
- `device.revoked {}` then the socket closes
- `host.state { locked: bool, attended: bool, on_battery: bool, stream_available: bool }`
- `stream.state { session, state: "requested|approving|launching|window_found|streaming|paused|ended", reason, window: { title, width, height, dpi } }`
- `stream.offer { session, sdp }`, `stream.ice { session, candidate }`

Client -> server:
- `stream.answer { session, sdp }`, `stream.ice { session, candidate }`
- `stream.resize { session, width, height }` (fit-to-phone; host resizes the window if allowed)
- `stream.pause { session }`, `stream.resume { session }`
- `ping {}` (server answers `pong`)

### Stream (Phase 2; signalling defined now so clients can be built against it)

`POST /stream`
```json
{ "share": "shr_...", "path": "Clients/Acme/Deck.pptx", "app": null,
  "viewport": { "width": 1080, "height": 2280, "dpr": 2.625 }, "prefer": { "codec": "h264", "max_kbps": 8000 } }
```
-> 201 `{ "session": "ses_01J...", "state": "requested", "app": { "id": "powerpoint", "name": "Microsoft PowerPoint" }, "needs_approval": false }`
or 403 `permission_denied`, 409 `stream_busy`, 412 `host_locked | host_unattended | app_unavailable`,
422 `stream_refused`. Then everything continues over `/events`. Media and input use WebRTC:

- Host is the offerer. One video track (H.264 baseline/main or HEVC by `prefer`), optional audio
  track (Opus) when `capabilities.stream.audio`, two data channels: `input` (unordered, max
  retransmits 0, pointer moves) and `control` (ordered, reliable: key events, text, clipboard,
  resize acks).
- ICE: host candidates only, on the addresses the host serves. No STUN/TURN/mDNS candidates. The
  client's answer likewise; ICE-lite on the host is acceptable.
- DTLS fingerprints travel in the SDP over the pinned TLS channel; that is their trust anchor.

`DELETE /stream/{session}?close_app=false` -> 204. `close_app=true` is honoured only if the host
launched the app for this session and the window is the only one of that process.

Input messages on the `input`/`control` channels are compact JSON (binary encoding is a later
optimisation):
```
{ "t": "move", "x": 0.4321, "y": 0.7788 }          // normalised to the captured window, 0..1
{ "t": "down"|"up", "b": "left|right|middle", "x": .., "y": .. }
{ "t": "scroll", "dx": 0, "dy": -120, "x": .., "y": .. }
{ "t": "key", "code": "KeyA", "down": true, "mods": ["ctrl"] }   // W3C UI Events code values
{ "t": "text", "s": "typed locally" }               // injected as Unicode (KEYEVENTF_UNICODE)
{ "t": "clipboard.get" } -> { "t": "clipboard", "s": "..." }   // text only, host-side opt-in
{ "t": "clipboard", "s": "..." } -> { "t": "clipboard.ack", "bytes": 12 }
```

**Sound (WP-55).** A host with `capabilities.stream.audio` adds one `sendonly` audio
m-section to the offer, after the video and in the same BUNDLE: Opus, payload type 111,
`opus/48000/2`, `minptime=10;useinbandfec=1`, 20 ms frames, about 64 kbit/s VBR. It carries the
sound of the streamed window's own process tree only (WASAPI process loopback, Windows 10 2004 or
later), never the computer's whole mix. The host captures only while the session streams (the
phone looking, `control` alive, not paused) and the phone has not muted it; otherwise nothing is
captured or encoded. On `control`:

```
{ "t": "mute", "on": true }                          // phone -> host: stop (true) or restart the sound
{ "t": "audio", "on": false, "reason": "muted" }     // host -> phone: on every change
```

`reason` is `muted`, `paused` (not streaming), `unavailable` (no sound this session: process
loopback could not start; there is no fallback to a system-wide capture) or `none` (this host
sends no sound, `[stream] audio = false`). The host repeats its `audio` state after the phone's
first `control` message, and a new engine session after a reconnect starts unmuted, so a phone
that muted sends `mute` again. A client that does not know `audio` ignores it and simply plays
the track.

**Clipboard text (WP-56).** Off unless the owner sets `[stream] clipboard` to `to_phone`
(the phone may read the computer's clipboard), `from_phone` (it may write it) or `both`; the
host advertises the setting as `capabilities.stream.clipboard` (omitted when `off`) and a client
shows its "Copy from computer" and "Paste to computer" actions only for the directions that are
on. Rules, all enforced on the host:

- Messages travel on the `control` channel only (a clipboard message on `input` is refused as
  `wrong_channel`). Text only, at most 64 KiB (65 536 bytes) of UTF-8, never truncated: a text
  over the cap is refused whole, in both directions. An empty text or a NUL character is refused.
  The data-channel message ceiling is 256 KiB (the SCTP maximum, negotiated in the SDP) so a
  64 KiB text still fits once JSON has escaped it. Line ends are `\n` on the wire; the host
  converts to and from the Windows `\r\n`.
- The host answers a `clipboard.get` with `clipboard`, a write with `clipboard.ack`, and any
  refusal with `{ "t": "clipboard.refused", "op": "get" | "set", "reason": <code> }`. Reasons:
  `disabled` (the owner's setting), `host_locked`, `phone_background`, `focus_lost`,
  `local_user_active` (the stream is not active: the same gate and codes as `input.refused`, the
  session-lock probe included, fail closed), `too_large`, `no_text`, `invalid_text`, `busy`
  (another application held the clipboard through the retries), `unavailable`. A client that does
  not know a reason treats it as a failure.
- The host never pushes its clipboard: a client drops a `clipboard` message it did not ask for.
- Every request is audited (`clipboard`: direction `to_phone` or `from_phone`, session, size or
  refusal reason, never the text) and a transfer shows a native notification on the computer
  ("Pixel 9 copied text from this computer").

## Pagination and caching summary

| Resource | Cache | Validation |
| --- | --- | --- |
| list | client may cache for offline display, marked stale | ETag / If-None-Match |
| thumb | immutable by ETag | none needed |
| preview page | immutable by ETag + page + width | none needed |
| preview tile | immutable by ETag + page + level + x + y | none needed |
| file | resumable by ETag + Range | If-Range |
| /me, /shares | re-fetch on connect and on `shares.updated` | none |

## Compatibility rules

- Clients ignore unknown JSON fields and unknown event types.
- Hosts ignore unknown query parameters.
- A client that needs a capability the host lacks must say so in the UI, not fail silently.
- The protocol number only changes for incompatible changes to existing fields or semantics.
